# 服务管理

项目当前有 **2 个 HTTP 服务和 1 个计划任务**。分时、网格、T+1 训练与选股日记并不是
四个独立服务器，而是共享行情缓存、搜索索引和 API 的四个业务入口。

| 运行单元 | 默认地址 | 职责 | 是否常驻 |
|---|---|---|---|
| 交互 Web | `127.0.0.1:8765` | 分时查询、T+0 网格回放、T+1 交易训练、选股日记及其 API | 是 |
| 静态报告 | `127.0.0.1:8000` | 兼容原有索引和静态 HTML 报告 | 是 |
| 每日更新 | 工作日 18:30 | 更新缓存、执行质量校验并刷新报告 | 否，按计划运行 |

## 一键启动与查看状态

所有命令都从项目根目录执行：

```bash
# 一键启动两个 HTTP 服务；不会触发耗时的数据更新
python -m scripts.serve

# 等价写法
python -m scripts.serve start all

# 查看两个服务和每日更新任务的真实状态
python -m scripts.serve status
```

日志位于 `output/logs/interactive_web.log` 和
`output/logs/static_reports.log`。进程记录位于 `cache/services/`，它们属于运行时
状态，不提交 Git。

## 按功能单独启动

```bash
python -m scripts.serve start minute
python -m scripts.serve start grid
python -m scripts.serve start trainer
python -m scripts.serve start journal
python -m scripts.serve start web
python -m scripts.serve start reports
```

前四条会分别给出对应页面地址，但底层都会启动同一个 `web` 进程。这是有意的：
它们共用同一份行情和搜索索引，拆成多个进程只会重复占用内存，并增加端口与版本不一致的
概率。

业务入口如下：

- 分时查询：<http://127.0.0.1:8765/minute_view.html>
- 网格回放：<http://127.0.0.1:8765/grid_simulator.html>
- T+1 训练：<http://127.0.0.1:8765/trading_trainer.html>
- 选股日记：<http://127.0.0.1:8765/stock_journal.html>
- 静态导航：<http://127.0.0.1:8000/index.html>

## 停止、重启与端口冲突

```bash
python -m scripts.serve stop web
python -m scripts.serve restart web
python -m scripts.serve stop all
```

统一入口默认只停止由它自己启动的进程。若 8765 被本项目的历史服务占用，状态会显示
“旧/错误服务占用”，可运行：

```bash
python -m scripts.serve restart web --replace-conflicts
```

该参数会先核对进程命令和工作目录，只替换本项目已知的旧服务；如果端口属于无关程序，
命令会拒绝终止它。8000 若显示“launchd/外部管理”，普通 `stop reports` 不会卸载外部
LaunchAgent，避免管理权混乱。

## 每日数据更新不是服务

每日更新只应在收盘后运行一次，因此不包含在 `start all` 中。手动执行或诊断仍使用：

```bash
python -m scripts.update_cache
python -m scripts.update_cache --validate-only
```

macOS 上的 `com.stock.cache-update` 只在工作日 18:30 唤起，任务结束后显示“当前空闲”
是正常状态，不代表定时任务失效。

## 开发模式

需要临时端口或希望前台查看请求日志时，可以直接运行底层服务：

```bash
python -m scripts.services.minute_viewer --serve --port 8877
```

日常使用推荐统一入口，避免再次出现旧静态服务器与新版 API 服务同时占用 8765 的情况。
